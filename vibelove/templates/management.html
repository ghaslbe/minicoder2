Ablauf

Nachricht schreiben → der Product Owner macht daraus einen Vorschlag inkl. Akzeptanzkriterien → „Jetzt bauen" → mc.py baut → ein automatischer QA-Lauf prüft das Ergebnis gegen die Kriterien und lässt bei Fehlern automatisch (bis zu dreimal) nachbessern.

Nur Backend, kein Frontend

Es muss kein separates Frontend geben. Sag das im Chat direkt so ("nur eine REST-API, kein Frontend"), dann baut mc.py ausschließlich einen backend/-Ordner mit vibelove-backend.json. Die Vorschau leitet in dem Fall automatisch komplett an das Backend weiter, statt einen Vite-Server zu erwarten.

Projekte: klonen, löschen, im Hintergrund weiterlaufen lassen

Über das ⋯-Menü neben der Projektauswahl: ein Projekt klonen (inkl. voller Git-Historie), löschen, oder per Häkchen 🔁 Im Hintergrund weiterlaufen lassen dafür sorgen, dass es beim Wegwechseln nicht beendet wird (bekommt dann einen eigenen, festen Port statt sich den Standardport mit anderen Projekten zu teilen).

HTTP-API (von aussen ansprechbar)

Vibelove hat keine eigene, separat dokumentierte "externe API" — es sind exakt dieselben JSON-Endpunkte, die auch diese Oberfläche selbst benutzt (alle unter http://<host>:5050, Body/Response ist JSON ausser bei /build). Alle Aktionen beziehen sich immer auf das aktuell aktive Projekt, ausser wo ein Projektname explizit als Parameter genannt ist.

Achtung: Diese Endpunkte haben aktuell keine Authentifizierung — jeder mit Netzwerkzugriff auf diesen Port kann Projekte anlegen, bauen, Dateien ändern und löschen. Für rein lokale Nutzung unkritisch; wer Vibelove darüber hinaus erreichbar macht (der Server bindet an 0.0.0.0), sollte das vorher absichern.

Schnellstart — Projekt anlegen und bauen lassen:

# Projekt anlegen (wird gleich aktiv)
curl -X POST http://<host>:5050/projects \
  -H "Content-Type: application/json" \
  -d '{"name":"mein-projekt"}'

# Bauen lassen (Product-Owner-Dialog optional, direkt eine Anweisung geben).
# Antwort ist ein Text-Stream (mc.py's Live-Ausgabe), kein JSON am Ende --
# alternativ nebenbei /build-status pollen.
curl -X POST http://<host>:5050/build \
  --data-urlencode "instruction=Baue eine REST-API für ..." \
  --data-urlencode "acceptance=1. ...
2. ..."   # optional -- ohne das kein QA-Loop

# Laufenden Bau abbrechen / Zwischenstand pollen (falls man den Stream nicht mitliest)
curl -X POST http://<host>:5050/build/stop
curl http://<host>:5050/build-status

Projekte verwalten:

GET /projectsAlle Projektnamen, aktives Projekt, keep_running-Status je Projekt, Vorschau-Port des aktiven Projekts.
POST /projects{name} — legt an, macht sofort aktiv (frisches Git-Repo).
POST /projects/aktiv{name} — wechselt das aktive Projekt.
POST /projects/clone{source, name} — Kopie inkl. voller Git-Historie, wird aktiv.
POST /projects/delete{name} — unwiderruflich; weder workspace noch das aktive Projekt.
POST /projects/keep-running{name, keep_running} — reserviert/gibt frei ein eigenes Port-Paar, s. oben.
GET /download-zipAktives Projekt als ZIP-Datei.

Bauauftrag / Product Owner:

POST /refine{message, mit_verlauf} — ein Schritt des PO-Dialogs; Antwort ist {type: question|spec|plan|error, ...} (bei spec inkl. instruction + acceptance).
POST /refine/resetSetzt den PO-Gesprächsverlauf zurück.
POST /builds. Schnellstart oben.
POST /build/stopBricht den laufenden Bauauftrag ab.
GET /build-status{laeuft, letzte_zeilen} — Zwischenstand ohne den Stream mitzulesen.
GET /bauverlaufAnweisung+Ergebnis je Bauschritt dieser Sitzung (Chat-Rekonstruktion).

Dateien:

GET /projects/filesAlle Dateien des aktiven Projekts (Pfad + Größe).
GET /projects/file?path=...Inhalt einer Datei (Text bis 2 MB, sonst nur binary:true).
POST /projects/file{project, path, content, revision} — speichert (Revisions-Prüfung gegen gleichzeitige Änderungen).
POST /projects/uploadMultipart-Datei-Upload in ein Unterverzeichnis.

Git:

GET/POST /projects/remoteOrigin-URL lesen/setzen (leer = entfernen).
POST /projects/pushPusht HEAD zu Origin.
GET /projects/git-logCommit-Historie (Hash, Datum, Message, verwendetes Modell).
POST /projects/rollback{commit} — git reset --hard + clean -fd auf einen Commit.

Einstellungen / Modelle / Skills:

GET/POST /settingsAktives Modell, Endpunkt, Schrittlimit, Token-Limit (API-Key nur setzbar, nie auslesbar).
GET/POST /profilesModellprofile anlegen/ändern/löschen (Name, Modell, Endpunkt, Key, Limits, weitere Modelle zum Umschalten).
POST /projects/profileWeist dem aktiven Projekt ein Profil zu.
GET/POST /skillsVorlagen anlegen/ändern/löschen (projektbezogen, geteilt, oder global).

Vorschau / Sonstiges:

POST /restart-viteVorschau (Vite/Backend) des aktiven Projekts hart neu starten.
GET /preview-statusPhase + Log des Vorschau-Starts.
POST /resetNur den Chat-Kontext zurücksetzen (kein Git).
POST /generate-containerErzeugt Dockerfile/Compose-Setup für das aktive Projekt.

Skills

Unter „Skills" lassen sich wiederverwendbare Vorlagen anlegen (projektbezogen, für alle Vibelove-Projekte, oder global) und im Chat per /skillname aufrufen.
